## 2. Release Summary

CSMS v1.0.0 is a web application that helps community services staff manage **Residents** and the **Service Requests** they submit.

Staff can:
- register, search, update and deactivate Residents
- submit Service Requests for Active Residents, then search, filter and view them
- move each request through a controlled workflow: Pending → In Progress → Completed, with Cancel allowed from the open states
- see a live Dashboard that summarizes the whole system

All data is stored in a SQLite database. Every business rule (validation, Resident eligibility, allowed status changes) is enforced on the server, not only in the browser. The running application identifies itself as version **1.0.0** on `/health` and in the footer of every page.

## 3. Resident Management Capabilities

- **Register a Resident** with first name, last name, address, contact number and email.
  - The ID is generated by the database.
  - Every new Resident starts as **Active**.
- **Validation** rejects:
  - a blank first name, last name or address
  - a contact number that is not in `09XXXXXXXXX` format
  - an invalid email

  Errors are shown next to the form, and the entered values are kept.
- **List and search** Residents by first or last name. The search is partial, ignores letter case, and trims extra spaces. The list is ordered by last name, then first name, then ID. A blank search shows everyone.
- **Update** a Resident's editable information. The ID and status cannot be changed through the edit form, and an invalid update saves nothing.
- **Deactivate** an Active Resident. This is a *soft* deactivation: the Resident stays in the database, still appears in the list and search results, and is shown as **Inactive**. Deactivating again is safe and changes nothing. There is no reactivation and no physical delete.

## 4. Service Request Management Capabilities

- **Submit a Service Request** with Resident ID, service type, description and date requested.
  - The ID is generated by the database.
  - Every new request starts as **Pending**.
- **Submission protection:**
  - blank or invalid fields are rejected
  - a Resident ID that does not exist is rejected ("Resident not found")
  - a Resident who is **Inactive** cannot submit new requests

  A rejected submission saves nothing.
- **List, search and filter.**
  - Text search covers the service type and description. It is partial, ignores letter case, and trims extra spaces.
  - The status filter offers All, Pending, In Progress, Completed and Cancelled, and it can be combined with text search.
  - Results are ordered by date requested (newest first), then by ID (highest first).
- **Details page** showing the ID, Resident ID, service type, full description, date requested and status.
- **Controlled workflow:**

  | From | Allowed actions |
  |---|---|
  | Pending | Start Processing (→ In Progress), Cancel (→ Cancelled) |
  | In Progress | Complete (→ Completed), Cancel (→ Cancelled) |
  | Completed / Cancelled | None — these are final states |

  Only the allowed buttons are shown. A crafted request for a forbidden change (for example Pending → Completed) is still rejected by the server, and the stored status does not change.

## 5. Dashboard Capabilities

The Dashboard (`/dashboard`) is read-only. Every number is counted by the database at the moment the page loads.

- **Resident Summary:** Total, Active and Inactive Residents.
- **Service Request Summary:** Total, Pending, In Progress, Completed and Cancelled, plus **Open Service Requests** (Pending + In Progress). Open is calculated, not stored.
- **Recent Service Requests:** the 5 most recent requests (newest date first, then highest ID), each with a **View** link to its details page.
- Shared navigation links the Dashboard, Residents and Service Requests pages.

## 6. Quality and Hardening

**T15 (system hardening)** reviewed the whole system and fixed two real defects:
- A malformed request body (for example broken JSON) used to cause a 500 error. It now returns a controlled **400 "Invalid Request"** page.
- The search characters `%` and `_` used to act as "match anything" wildcards. They are now searched for literally.

T15 also put the list of Service Request statuses in one place and added five hardening tests.

**T16 (final release)** added:
- one authoritative release version (`package.json` → `1.0.0`), used by `/health` and by the version shown on every page
- automated tests that check the release identity
- a final integration test that runs a Resident's full service history and then restarts the application to confirm all data and views still agree
- a full manual acceptance check

## 8. Known Limitations

These are outside the defined CSMS scope and were carried forward from T15:

1. **Unknown URLs return JSON, not an HTML page.** The starter contract answers unknown routes with `{"status":"error","message":"Resource not found"}`. Not-found pages *inside* the Resident and Service Request screens are proper HTML pages.
2. **No login, authentication or CSRF protection.** These are out of scope for the CSMS.
3. **Case-insensitive search covers English letters only.** SQLite ignores letter case only for A–Z, so letters such as `Ñ`/`ñ` match only in the same case.
4. **No concurrent-edit detection.** If two staff members edit the same Resident at the same time, the last save wins.
5. **Runtime version.** The project targets Node.js 24 (`.nvmrc`). This release was verified on Node.js 22.20.0, where `node:sqlite` prints a harmless "experimental feature" startup warning.
6. **The home page (`/`) still shows the original starter text** ("Sprint 0 - Developer Onboarding"). The starter tests check that text, and no ticket asked for it to change. The home page does show the correct version, 1.0.0.

No known release-blocking limitations remain within the defined CSMS v1.0.0 scope.
